# Общие требования к микросервисам платформы

Этот документ получает каждая команда вместе с заданием на свой сервис (`brief.md`). Здесь - правила, одинаковые для всех сервисов: как
устроен контракт, как сервис поставляется, что считается качеством и как проходит приёмка.
Задание сервиса может ужесточать эти правила, но не отменять.

## 1. Контекст в двух абзацах

Мы делаем платформу для наружной рекламы: карта и каталог рекламных конструкций (щиты,
экраны, транспорт), календарь занятости, заказы, программатик. Платформа - монолит на Laravel и
React, у неё свой стек и свои правила, менять её вы не будете.

Ваш сервис - **отдельное приложение**, которое платформа вызывает по HTTP. Она присылает
данные (файл, ссылку на файл в S3, параметры) и получает результат сразу либо позже через
callback. Сервис не ходит в базу платформы, не знает её сущностей и не принимает бизнес-решений:
он считает, проверяет, преобразует и честно отвечает, что получилось.

## 2. Контракт HTTP

- **Версия в пути**: все маршруты под `/v1/`. Ломающее изменение - новая версия рядом, старая
  живёт до вывода из эксплуатации.
- **JSON, UTF-8**, `Content-Type: application/json`; файлы - `multipart/form-data` или по ссылке.
- **Неизвестные поля игнорируются**, перечисления открытые (клиент обязан переживать новые
  значения). Это позволяет развивать API без ломки.
- **Ошибки** - единая форма: `{ "error": "machine_slug", "message": "текст для человека",
  "details": { ... } }`. Слаги - латиницей в `snake_case`, тексты - по-русски. Коды: `400` кривой
  запрос, `401` нет или плохой токен, `403` токену нельзя, `404` нет объекта, `409` конфликт
  состояния, `413` слишком большой файл, `422` тело валидно синтаксически, но не по смыслу,
  `429` лимит (с `Retry-After`), `5xx` сбой сервиса.
- **Долгие операции - задания (jobs)**: `202 Accepted` с `{ "job_id": "...", "status_url": "..." }`,
  затем `GET /v1/jobs/{id}` со статусом `queued | running | succeeded | failed`, прогрессом
  (0-100 или шаги) и результатом или ошибкой. По желанию клиента - **callback** (`callback_url`
  в запросе): `POST` с результатом, подписанный (см. ниже), с повторами при ошибке (не меньше
  5 попыток с нарастающей задержкой). Клиент может опрашивать статус и получать callback
  одновременно - результат обязан быть идемпотентным.
- **Идемпотентность**: повтор того же запроса не создаёт второй результат. Механизм -
  заголовок `Idempotency-Key` или дедупликация по содержимому (хэш файла + параметры). Какой
  именно - описать в API.
- **Пагинация** списков - курсором (`cursor` / `next_cursor`), кап размера страницы.
- **Время** - ISO 8601 с таймзоной. **Идентификаторы** - непрозрачные строки. **Денег** в API нет.
- **Заголовок `X-Request-Id`**: принимаем от клиента или генерируем, возвращаем в ответе, пишем в лог.
- **OpenAPI 3.1** в репозитории (`openapi.yaml`) - источник правды по контракту: с примерами
  запросов и ответов, проверяется тестами (контрактные тесты или генерация из кода). Swagger UI
  на `/docs` в dev-режиме.

## 3. Аутентификация и подписи

- **Вызовы в сервис** - `Authorization: Bearer <token>`. Токенов может быть несколько, у каждого
  область (`admin`, `write`, `read`), отзыв без перезапуска. Токены хранятся хэшем.
- **Callback'и из сервиса в платформу** подписываются так же, как вебхуки самой платформы:
  заголовки `X-Apc-Timestamp` (unix-секунды) и
  `X-Apc-Signature: sha256=HMAC_SHA256("{timestamp}.{raw_body}", secret)`; подпись считается от
  сырого тела запроса. Платформа отвергает подпись старше 5 минут.
- **Публичные ссылки** (тайлы карты, превью файлов) - только подписанные URL со сроком
  действия (HMAC от пути и `exp`), если задание не говорит иначе.
- Секреты - только через переменные окружения. В репозитории - `.env.example` с пустыми
  значениями и комментарием к каждой переменной.

## 4. Поставка и запуск

- **Docker**: multi-stage сборка, запуск не от root, `HEALTHCHECK`, образ с зафиксированными
  версиями зависимостей. Один сервис = один репозиторий = один образ (воркеры - тот же образ с
  другой командой).
- **`docker compose up`** поднимает всё нужное для локального запуска (сам сервис, воркеры,
  БД, очередь, MinIO вместо S3 и т.п.) на чистой машине за одну команду. Миграции применяются
  автоматически или одной документированной командой.
- **Конфигурация только через env**, все переменные перечислены и объяснены в `.env.example`
  и README. Профиль **«маленький сервер»** - 2 vCPU / 4 ГБ ОЗУ, без GPU, Linux x86_64 - обязан
  работать (пусть медленнее). GPU, если используется, - ускорение, а не требование.
- **Служебные ручки**: `GET /health` (жив, версия сборки), `GET /ready` (готов: зависимости
  доступны), `GET /metrics` в формате Prometheus (желательно: счётчики запросов, длительности,
  очередь, кэш).
- **Логи** - структурированные (JSON) в stdout, с `request_id`, без персональных данных и
  секретов. Уровни настраиваются.
- **Лимиты**: размер файла, длительность обработки, число одновременных заданий - в конфиге;
  при исчерпании сервис отвечает `429`/`503` с `Retry-After`, а не падает. Корректное завершение
  по SIGTERM (текущее задание доделывается или помечается для повтора).

## 5. Качество кода и репозитория

- Тесты: юнит на ядро (разбор, математика, проверки) и интеграционные на API (поднятый сервис
  в тестовом режиме). CI (GitHub Actions) гоняет тесты и линтер на каждый push; зелёный CI -
  условие приёмки.
- Линтер и форматтер по стандарту языка, зафиксированные версии зависимостей (lock-файл).
- `README.md`: запуск за 10 минут, архитектура на одну страницу (схема компонентов и поток
  данных), конфигурация, эксплуатация («что делать, если...»), ограничения.
- `docs/decisions.md` - принятые решения (мини-ADR: контекст, решение, последствия);
  `docs/questions.md` - открытые вопросы заказчику; `CHANGELOG.md`.
- Никаких секретов в истории git (проверка `gitleaks` или аналог в CI).
- Лицензии зависимостей совместимы с закрытым коммерческим использованием. Внешние бинари
  (ffmpeg, GDAL) - вызовом процесса, это нормально; библиотеки с требованием раскрытия нашего
  кода не подключаем без согласования.
- Язык: тексты для людей (сообщения, документация) - русский; идентификаторы, слаги, код,
  комментарии в коде - на усмотрение команды, но единообразно.

## 6. Безопасность

- **Любой входной файл - враждебный.** Лимиты размера и времени разбора, разбор в отдельном
  процессе с ограничением памяти и CPU, без доступа в сеть, где это возможно. Декомпрессионные
  бомбы (zip, изображения), полиглоты, кривые заголовки не должны валить сервис - только задание.
- Внешние утилиты вызываются с аргументами массивом, без сборки командной строки из данных.
- Загрузка по ссылке - защита от SSRF: только `http(s)`, запрет внутренних и локальных
  адресов, ограничение редиректов и размера, таймауты.
- Rate limit на публичных и дорогих ручках; capы одновременных заданий на токен.
- Персональные данные (голос, лица, тексты) - по минимуму, с настраиваемым сроком хранения
  и ручкой удаления; вне России не отправляем без явной настройки.

## 7. Производительность

Ориентиры по скорости и качеству даны в задании сервиса. Замеры делаются **скриптом из
репозитория** (k6, hey, locust или аналог) на объявленном профиле железа, результаты - таблицей
в отчёте: что мерили, на чём, сколько получилось, где узкое место. Цифры «на глаз» не принимаются.

## 8. Процесс работы

| Этап | Что сдаётся | Срок (ориентир) |
|---|---|---|
| **M0. Дизайн** | Design doc (2-4 страницы): границы сервиса, черновик API, схема данных, стек с обоснованием, риски, план этапов. Согласуется до начала кода | 1-2 недели |
| **M1. Вертикальный срез** | Один сквозной сценарий работает в Docker: вход → обработка → результат через API, минимальные тесты | 3 недели |
| **M2. Полный объём** | Все «обязательно» из задания, OpenAPI, тесты, callback'и, лимиты | 3-4 недели |
| **M3. Закалка** | Замеры и оптимизация, отчёт о замерах и качестве, документация, runbook, демо | 2 недели |

Демо заказчику раз в две недели (15 минут: что сделано, что дальше, какие вопросы). Стек
выбирает команда и защищает в M0; заказчик вправе отклонить выбор, если он мешает эксплуатации
(экзотика без пакетов, нет Docker-образов, лицензии).

## 9. Приёмка

Подробных критериев приёмки команда заранее не получает - намеренно: цель - хороший сервис, а не
сервис, подогнанный под чек-лист. Порядок такой:

1. Заказчик клонирует репозиторий на чистую машину, выполняет `docker compose up` по README -
   сервис поднимается, `/health` и `/ready` отвечают.
2. Проходит сквозной сценарий из задания на своих данных, в том числе на тех, которых команда не
   видела, - через интерфейс или коллекцию запросов из репозитория.
3. Смотрит отчёт команды о замерах и качестве и сверяет его со своими ориентирами; при расхождении
   команда объясняет причину.
4. Ревью кода: читаемость, тесты, отсутствие секретов, обработка ошибок, соответствие OpenAPI.
5. Передача: как обновлять, как ротировать токены, известные ограничения и долги
   (`docs/known-issues.md`).

Сервис считается принятым, когда выполнены общий чек-лист (разделы 2-7) и всё «обязательно» из
задания; «желательно» не блокирует приёмку, но фиксируется как сделанное или нет.
