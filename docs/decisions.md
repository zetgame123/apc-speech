# Архитектурные решения (Architecture Decision Records)

## ADR-001: Выбор `faster-whisper` как единственного локального ASR-движка
* **Статус**: Принято
* **Контекст**: Требуется высокое качество распознавания русской речи (WER $\le 12\%/25\%$), поддержка таймкодов, пунктуации и терминов на 2 vCPU без GPU. Внешние ASR строго запрещены.
* **Решение**: Использовать библиотеку `faster-whisper` (рантайм CTranslate2 с int8 квантованием). В качестве весов использовать оптимизированный для русского языка чекпоинт `whisper-podlodka-turbo-ct2` (для длинных аудио) и облегчённый `whisper-small` (для голосового поиска с SLA $\le 2{,}5$ с).
* **Последствия**: 4-кратный прирост скорости по сравнению с OpenAI Whisper, возможность запуска модели `small` в $\approx 700$ MB RAM, что гарантирует работу на профиле `small`, и высокая точность на русской бизнес-терминологии благодаря чекпоинту Podlodka Turbo.

## ADR-002: Использование единой СУБД PostgreSQL 16 с `pgvector`
* **Статус**: Принято
* **Контекст**: Сервису требуются: реляционная модель звонков, хранение JSONB, полнотекстовый поиск по русской речи и хранение векторных эмбеддингов для кластеризации.
* **Решение**: Использовать PostgreSQL 16 с официальным расширением `pgvector`.
* **Последствия**: Отказ от поднятия отдельных сервисов Elasticsearch и Milvus/Qdrant. Экономия $\approx 1{,}5$ GB RAM на профиле `small`, отсутствие распределенных транзакций.

## ADR-003: Разделение очередей на Fast-Track и Long-Job
* **Статус**: Принято
* **Контекст**: Длинные 3-часовые звонки могут полностью занять пул воркеров, блокируя интерактивный голосовой поиск с SLA $\le 2{,}5$ с.
* **Решение**: Физически разделить воркеры на `worker-fast` (чистая оперативная память, модель всегда прогрета) и `worker-long` (пакетная обработка через Redis Streams).
* **Последствия**: Голосовой поиск гарантированно получает ресурсы даже при 100% загрузке очереди пакетных задач.

## ADR-004: Изоляция внешнего LLM-провайдера за портом с принудительным PII-маскированием
* **Статус**: Принято
* **Контекст**: Допускается внешний LLM-провайдер для аналитики, но аудио и ПДн никогда не должны попасть во внешнюю сеть.
* **Решение**: Архитектура портов и адаптеров (`AnalysisModelPort`). Внешний адаптер отключен в коде по умолчанию (`LLM_EXTERNAL_PROVIDER_ENABLED=false`). В адаптер передается только `MaskedTranscript`, где все телефоны, имена и реквизиты заменены плейсхолдерами.
* **Последствия**: Полная безопасность и соответствие 152-ФЗ / GDPR даже при случайном включении флага в конфиге.

## ADR-005: Обработка автоответчиков и IVR
* **Статус**: Принято
* **Контекст**: Значительная часть неудачных звонков приходится на автоответчики («абонент временно недоступен», гудки), тратить ресурсы LLM на которые бессмысленно.
* **Решение**: Детектировать автоответчик на первых 15 секундах по ключевым паттернам, выставлять флаг `is_answering_machine=true` и пропускать этап LLM-анализа, сохраняя базовый транскрипт.
* **Последствия**: Экономия до 40% вычислительных ресурсов на пакетной обработке звонков.

## ADR-006: Раздельные сроки хранения (Retention)
* **Статус**: Принято
* **Контекст**: Аудиозаписи занимают большой объем в MinIO и содержат биометрические ПДн, в то время как обезличенный текст необходим для долгосрочной аналитики.
* **Решение**: По умолчанию удалять аудиофайлы через 14 дней, сохраняя текстовые транскрипты в течение 365 дней.
* **Последствия**: Оптимальный баланс между расходом дискового пространства и аналитической ценностью данных.

## ADR-007: Обработка синхронного голосового поиска (выделенная fast-очередь `worker-fast`)
* **Статус**: Принято (пересмотрено)
* **Контекст**: Для голосового поиска требуется жесткий SLA $\le 2{,}5$ с на 2 vCPU. Выполнение ASR внутри процесса `api` конкурирует за CPU/память с остальными запросами и усложняет изоляцию задержки при параллельной нагрузке.
* **Решение**: `api` помещает запрос в отдельный Redis Stream `jobs:audio:fast` и ждёт ответ от обязательного (не опционального) воркера `worker-fast` не дольше `VOICE_SEARCH_RESULT_TIMEOUT_SEC`; при переполнении/таймауте возвращается `503` с `Retry-After`. In-process путь через `asyncio.to_thread` и семафор (`VOICE_SEARCH_MAX_CONCURRENCY`) сохранён как explicit fallback только для локальной разработки и unit-тестов (`VOICE_SEARCH_USE_WORKER=false`), в Docker-профилях не используется.
* **Последствия**: ASR-инференс изолирован от процесса `api` даже в компактном профиле `small`; фактические замеры задержки и аппаратные ограничения — в `docs/benchmark-report.md`.

## ADR-008: `model-downloader*` запускаются от root (единственное исключение из «без root»)
* **Статус**: Принято
* **Контекст**: При первом запуске на чистой Linux-машине Docker Engine сам создаёт отсутствующую bind-mount директорию `./models` на хосте с владельцем `root:root` (режим `0755`). Непривилегированный `apcuser` (UID 10000) образа не может писать в неё, и `model-downloader`/`model-downloader-llm` падают с `PermissionError` при самой первой загрузке весов моделей (воспроизводится только на Linux-хосте; на Docker Desktop для Windows маскируется особенностями его bind-mount слоя).
* **Решение**: Для `model-downloader` и `model-downloader-llm` переопределён `user: "0:0"` в `docker-compose.yml`. Это единственное сознательное исключение из общего требования «контейнеры без root» (`common-requirements.md`, п.4): оба сервиса — одноразовые init-job без HTTP-порта и без обработки пользовательских данных, пишущие только заранее известные файлы моделей по фиксированным HTTPS-URL; `api`/воркеры/`llm-runtime`, принимающие трафик или пользовательские данные, остаются от `apcuser`.
* **Последствия**: `docker compose up` поднимается с одной команды на чистой машине без ручного `chown ./models` после `git clone`. Альтернатива (entrypoint-обёртка с `chown` от root и `gosu`/`su-exec` для понижения прав перед запуском скрипта) рассмотрена и отклонена как усложнение Dockerfile ради сервиса, который не обслуживает трафик.

## ADR-009: Скачивание аудио по URL перенесено из `worker-long` в `api`; сети `backend` (internal) и `frontend` разделены
* **Статус**: Принято
* **Контекст**: По B9 воркеры распознавания (`worker-long`, `worker-fast`) изолированы в сети compose `backend` с `internal: true` — у них нет выхода в интернет, аудио и модели полностью локальны. Но `POST /v1/jobs/by-url` и вебхук Битрикс24 (`RECORD_URL`) раньше скачивали внешнее аудио внутри `worker-long` (`source_url` в payload). После изоляции сети этот путь сломался бы, а приём по ссылке — обязательный пункт ТЗ (C1).
* **Решение**: Скачивание выполняет `api` (у него есть egress через сеть `frontend`) в новом helper `app/api/audio_ingest.py::fetch_url_to_s3`: SSRF-защита та же (`download_file_ssrf_safe` — по hop'ам, редиректы ≤3, лимиты размера, таймауты), файл стримится во временный файл и затем в MinIO, в БД создаются `Call`/`AudioObject`/`Job`, воркеру уходит payload с готовым `s3_key` (поле `source_url` удалено из обоих хендлеров и воркера). Топология сетей: `backend` (internal) — postgres, redis, minio, api, worker-long, worker-fast, worker-callback, llm-runtime, миграции, retention; `frontend` (default) — api, worker-callback, model-downloader. Воркерам добавлен `HF_HUB_OFFLINE=1`, чтобы рантайм не пытался тянуть веса/телеметрию из сети.
* **Последствия**: Плюс — B9 выполнен без потери C1; клиент сразу получает `202`
  (скачивание до 500 МБ идёт в фоне через `BackgroundTasks`, прогресс виден в
  `GET /v1/jobs/{id}`: `pending_download` → `downloaded`, при обрыве — `failed`
  + failure-callback как при падении воркера); топология покрыта
  `tests/test_compose_network.py`, фоновый ingest — `tests/test_audio_ingest.py`,
  быстрый 202 — тестами хендлеров. Минус — задание появляется в очереди воркера
  только после скачивания (задержка постановки = время скачивания + заливки в S3).
  Альтернатива (отдельный downloader-воркер с egress) отклонена как лишний сервис
  ради одной операции.

## ADR-010: Лицензия `bond005/whisper-podlodka-turbo-ct2` — Apache 2.0
* **Статус**: Принято
* **Контекст**: Основная ASR-модель длинных звонков (`scripts/download_models.py:273-276`,
  `ASR_MODEL_NAME` по умолчанию). По `AGENTS.md` п.5 коммерческое использование модели
  требует записи лицензии в `decisions.md`; в аудите A4 лицензия числилась неизвестной
  (`docs/questions.md`, `docs/gap-report.md`).
* **Решение**: Зафиксировать лицензию **Apache 2.0** — источник: карточка модели на
  Hugging Face (`bond005/whisper-podlodka-turbo-ct2`, поле License: apache-2.0, пустой
  README), подтверждено через HF API (`tags: ["license:apache-2.0"]`), проверено 2026-10-11.
  Apache 2.0 допускает коммерческое использование в закрытом продукте без раскрытия кода.
* **Последствия**: Пункт снят из списка сомнительных лицензий (`questions.md`, `gap-report.md`).
  Остаются открытыми: provenance `campplus.onnx`, AGPL MinIO, условия Qwen, словари Natasha.
  При смене весов лицензию сверять заново.

## ADR-011: Эксперимент T-one (t-tech/T-one) как движок быстрого пути (2026-10-11)

* **Статус**: Эксперимент (решение о замене не принято; дефолт — whisper-small)
* **Контекст**: C4 не укладывается в 2,5 с на whisper-small (п.8–9). T-one — стриминговый
  CTC Conformer 71M для русской телефонии, обещает низкую задержку на CPU.
* **Лицензия**: код **и** веса — **Apache 2.0** (GitHub LICENSE + HF-карточка t-tech/T-one
  `License: apache-2.0`, проверено 2026-10-11). Коммерческое закрытое использование допустимо.
* **Решение**: отдельный `ToneEngine` (`app/asr/tone_engine.py`) за тем же ASR-интерфейсом
  (`segments`/`metadata`), включается только `VOICE_SEARCH_ENGINE=tone` (дефолт `whisper`);
  веса `model.onnx` (144 МБ) тянет `model-downloader` в `models/t-one/`, воркер работает
  офлайн (`HF_HUB_OFFLINE=1`, сеть `backend` без egress).
  Используется только greedy-декодер: штатный `kenlm.bin` весит **5,5 ГБ** и неприемлем
  для small (документировано, не скачивается). Кастомный KenLM под словарь терминов
  возможен в принципе (`build_ctcdecoder(labels, kenlm_model_path, ...)` + свой arpa),
  но не делается в рамках эксперимента.
* **Зависимости**: новых нет. PyPI-пакет `tone==0.1.0` для продукта не подошёл: пустые
  `Requires-Dist` в метаданных и безусловный `import torch` (`tone.utils`) в `__init__`
  (torch для small-профиля неприемлем). Вместо зависимости — faithful-порт рантайма
  (чанкинг 2400 сэмплов @8 кГц, состояние, logprob-сплиттер, greedy-декодер) на уже
  имеющихся `onnxruntime`+`numpy`, с атрибуцией Apache 2.0 в шапке файла; валидация —
  посимвольное совпадение текстов с эталонным пакетом. Потоки задаются только через
  env (`OMP_NUM_THREADS`, своих ручек у рантайма нет).
* **Выход — строчные без пунктуации** (алфавит декодера: 33 буквы + пробел), вопрос в `questions.md`.
* **Последствия**: плюс — честное сравнение на том же стенде без новых зависимостей
  и без downgrade `huggingface-hub` (faster-whisper не тронут).

## ADR-013: Сумма CPU-лимитов 2,5 при 2 vCPU (2026-10-11)

* **Статус**: Принято (осознанный риск)
* **Контекст**: Лимиты `deploy.resources.limits.cpus` постоянных сервисов small:
  postgres 0,3 + redis 0,2 + minio 0,2 + api 0,4 + worker-long 0,6 +
  worker-callback 0,2 + worker-fast 0,5 + cleanup-retention 0,1 = **2,5 vCPU**
  при профиле 2 vCPU (память сходится: 4032M из 4096M).
* **Решение**: оставить как есть. Лимиты в Compose — это **потолки (ceilings),
  а не резервы**: сумма лимитов может превышать число ядер, планировщик делит
  фактическое время между контейнерами. Пиковая одновременная загрузка всех
  сервисов — редкость (тяжёлые только worker-long/worker-fast, и то по очереди).
* **Последствия (риск троттлинга)**: при совпадении пиков (ASR + запросы + записи
  в БД) контейнеры упрутся в CFS-квоты и замедлятся, но не упадут. Если замеры
  покажут систематический троттлинг long-очереди — резать лимиты фоновых сервисов
  (postgres/redis/minio) в пользу воркеров, а не наращивать сумму.

## ADR-014: Beam search для T-one — свой, без pyctcdecode/kenlm (2026-10-12)

* **Статус**: Принято
* **Контекст**: Для hotword-бустинга в T-one рассмотрен pyctcdecode 0.5.0.
  Проверено 2026-10-12: pyctcdecode — **Apache 2.0** (PyPI, Kensho; deps только
  numpy+pygtrie), подключать было бы можно. Но `pyctcdecode/decoder.py`
  содержит безусловный `import kenlm`, а KenLM — **LGPL-2.1**
  (`kpu/kenlm` LICENSE: «Most of the code here is licensed under the LGPL»).
* **Решение**: kenlm не подключать (копилефт — вопрос 4 в questions.md);
  как следствие, и pyctcdecode не подключать (без kenlm не импортируется).
  Вместо этого — компактный собственный prefix beam search с hotword-бонусом
  (~80 строк, только numpy) в `app/asr/tone_engine.py`, включается только
  `TONE_DECODE=beam` (дефолт greedy). Подмешивание словаря через KenLM остаётся
  возможным в будущем при решении по kenlm.
* **Последствия**: ноль новых зависимостей, образ не вырос; качество beam без LM
  честно замеряется против greedy в п.3б.
