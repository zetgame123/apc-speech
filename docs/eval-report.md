#### 5.1. П.1: диагноз нулей period/budget/category (2026-10-13, промпт v1.4)

(`reports/probe_qwen10_out.json`). Правила ДО: оба поля жёстко `None`,
бюджет — только `r"бюджет|до …000 руб"`.

Три причины, все подтверждены:
1. **Путь правил** (`app/llm/local_adapter.py::_analyze_via_rules`): поля
   `target_period`/`product_category` были жёстко `None`; бюджет ловился
   только с префиксами «бюджет/до». Исправление: экстракторы
   `extract_period` (месяц канонически, квартал, полгода, диапазон
   «с мая по сентябрь»), `extract_budget_rub` (число+валюта, «полмиллиона»
   → 500000, «двести тысяч» без валюты → 200000),
   `extract_category` (словарь `PRODUCT_CATEGORY_DICT`).
   Юнит-тесты: `tests/test_entities_extraction.py` (28 шт.: период-месяц,
   период-диапазон, бюджет число+валюта, бюджет словами, категория из словаря,
   анти-ложняки «макет≠май», «2 поверхности≠бюджет»).
2. **Путь Qwen** (схема + промпт v1.3-ru-compact): схема поля имеет, но промпт
   не задавал формат (число в рублях? месяц? словарь?) — модель ставила null.
   Исправление: явный блок «Сущности entities» (v1.4-ru-entities):
   quantity — целое; period — месяц/квартал/срок; budget_rub — ЧИСЛОМ
   («двести тысяч» → 200000); category — бизнес клиента.
3. **Оценщик** (`scripts/eval_types.py::_num`): выкидывал буквы —
   «200 тысяч рублей» → 200 ≠ 200000, верное предсказание считалось ошибкой.
   Исправление: симметричное приведение обеих сторон через
   `coerce_quantity`/`coerce_budget` (тысяч ×1000, миллион ×1e6,
   полмиллиона → 500000). Правила сопоставления описаны в docstring оценщика:
   city/format/period/category — нормализация (регистр, ё→е) + точное
   равенство/подстрока; quantity/budget — численное равенство после
   приведения; оба пусто — пара пропускается.

Перебрано вариантов промпта: 2 (v1.3 base, v1.4 +блок сущностей;
вариант 3 с примерами пар — в п.2).

Итог пересчёта (новый оценщик; precision/recall/F1 — в `reports/types_eval.json`):
- rules-A: period 1,0 / budget 1,0 / category 1,0 (было 0,0/0,0/0,0);
- rules-B: period 0,67 / budget 0,38 / category 0,0 — все 8 расхождений
  проверены вручную: текст сущность содержит, эталон B — None
  («выйдет примерно двести тысяч», «на двести тысяч, застройщик»,
  «пятьдесят тысяч», «щиты от восьмидесяти тысяч», «на полгода»).
  Аннотированных позитивов rules на B не пропустил ни одного;
- Qwen v1.4 Asub: budget 0,0→1,0, period 0,0→0,4 (путает месяцы:
  ноябрь→октябрь, «месяц», «first_quarter»), category 0,0 (модель
  переполняет: «застройщик»/«суперсайт»/«formats» в чужих местах);
- Qwen v1.4 B: budget 0,33, period 0,25, category 0,0 (те же галлюцинации

- побочка v1.4: cities/formats у Qwen просели (Asub city 1,0→0,63,
  format 0,5→0,1; B city 0,96→0,27) — модель тратит вывод на новые поля

#### 5.2. П.2: типы — матрица ошибок A, таксономия, примеры (промпт v1.5)

заново на каждый файл — медленно). Исправлено на корпусную агрегацию, как в
`evaluation/run.py`. Эффект на Golos-100 — ниже 4-го знака: пересчёт

Объяснение разброса 16–38%:
1. Домен: Golos — короткие команды с wake-словами (салют/джой/афина/сбер —

2. Длина: средняя фраза ~3,4 с / ~6 слов — одна ошибка wake-слова ≈ 15–17%
   файлового WER; слабые модели платят этот пол почти на каждой фразе.
3. Телефония (8 кГц + G.711 + bandpass): у whisper-моделей пропуски

по телефонии (≤ 25%) проходит только T-one (19,6%). Причины выше —

Свип (§12, `scripts/sweep_long.py`, конфиг A_base — продакшн worker-long
на тот момент): движок `AsrEngine(model_name="./models/whisper-podlodka-turbo-ct2")`,
`compute_type=int8`, `device=cpu`, `ASR_THREADS=2`; вызов
`transcribe(language="ru", beam_size=2, temperature=0.0, vad_filter=True,
word_timestamps=True)`, VAD-дефолт (`threshold=0.35, min_silence_duration_ms=450,
speech_pad_ms=300`), `initial_prompt` — conversation-дефолт
(`DEFAULT_CONVERSATION_PROMPT`, т.к. hints не передавались), `hotwords=None`,
вход — сырые байты файла без предобработки (кроме конфигов H/I).
Модель прогрета (`warmup()` до замера). Метрика long-RTF — wall только вокруг
одного вызова `transcribe()` на склейке ~93,6 с (`_concat_wav`, clean Golos-30):
`0,305` у A_base (`reports/long_sweep.json`). Время ffmpeg-предобработки
в RTF не входит (оговорка §12). Частота во время свипа плавала 1,09–4,29 ГГц
(без капа, `machine.ghz_min/max` в том же отчёте). RTF 1,6–2,6 на отдельных
3-секундных файлах в том же свипе — overhead на файл (загрузка/декод/VAD-сессии),
а не инференс.

Часовка (§16, `reports/hour_small_3ghz_2026-10-14.json`): тот же движок
и те же декодерные параметры (worker вызывает `transcribe` без `beam_size` —
дефолт движка 2; `word_timestamps=True`, VAD-дефолт, промпт-дефолт при пустых
hints), но метрика — server-side `created→updated` всего пайплайна 3600 с
при капе 3,0 ГГц (`scaling_max_freq=3000000`, факт ~2,99 ГГц, cpuset 4,6):
wall 5027,5 с = очередь 4 с + чанкинг 228 с (адаптивный VAD, 9 чанков,
`chunk_length_sec=600/overlap_sec=15` + ffmpeg `convert_to_pcm16` с loudnorm
до ASR) + ASR 3687 с (~73 % wall, 9 последовательных `transcribe` 600-секундных
чанков с `word_timestamps=True` и коммитом прогресса в БД после каждого) +
диаризация ~789 с (CAM++: загрузка сессии + эмбеддинги каждого turn +
Viterbi) + refinement/semantic ~320 с (включая один `ReadTimeout` llm-runtime
с повтором). Один только ASR-этап даёт 3687/3600 = **RTF 1,024** — уже выше
1,0 до диаризации и LLM.

Итого расхождение — не регрессия движка, а три разницы методики:
1. Объём метрики: чистый `transcribe()` склейки 94 с (0,30) против полного
пайплайна 3600 с (1,397), где ASR — лишь 73 %, остальное — чанкинг,
диаризация (~789 с), LLM (~320 с).
2. Частота: плавающая до ~4,29 ГГц в свипе против фиксированного капа 3,0 ГГц
в часовке (замедление wall 3431→5027 с, ×1,47 при снижении частоты в ~1,2–1,4×).
3. Амортизация overhead: один вызов на 94 с против 9 вызовов на 600-секундных
чанках + побайтовые DB-коммиты прогресса + `word_timestamps` на длинных
сегментах. Вывод для следующих пунктов: рычаги искать в ASR-чанках (beam,
VAD, размер чанков) и в диаризации моно, а не в «возврате 0,30» — 0,30
измеряло не то.

### §20. Диаризация: стерео с раздельными каналами и ускорение моно (п.3)

Проверено чтением кода (`app/workers/long_audio_processor.py:99–279`,
`app/diarization/mono_diarizer.py`, `app/diarization/roles.py`) и цифрами
DER-стенда из скриптов (`reports/der_suite.json`: моно DER 0,163 / роли 0,94
при медиане 28,7 с на файл 2–5 мин; стерео DER 0,286 / роли 0,98 при медиане
0,0 с — ноль секунд на саму диаризацию).

Стерео с раздельными каналами: диаризация НЕ нужна и НЕ выполняется —
уже факт кода, а не предложение. Стерео-ветка (`:157–229`) делит файл на
каналы, гоняет каждый через ASR и ставит роли мгновенным маппингом
(`assign_stereo_roles` — словарь + сортировка, миллисекунды); вызовов
`MonoDiarizer` в ветке нет (единственный вызов — `:273–277` в моно-ветке).
Перед ветвлением — дешёвая проверка изоляции `check_channel_isolation`
(первые 60 с, энергии + корреляция): dual-mono/микрофонный bleed честно
уходит в моно-ветку с CAM++. Отдельный стерео-VAD не нужен: сегментация
идёт внутри whisper-VAD каждого канала, перекрытия сохраняются поканально
(DER 0,286 — в основном пропуски TTS-паддингов эталона, см. §4).

Цена стерео-ветки — в другом месте: ASR ×2. Каждый канал транскрибируется
целиком и безусловно, т.е. стерео-час = 7200 с аудио через ASR против
моно-часа = 3600 с + ~789 с диаризации. При ASR RTF ~1,0 стерео-час
дороже моно-часа, несмотря на нулевую диаризацию. Резерв (не реализован,
отдельный пункт): energy-gating немых чанков канала — в телефонии одна
сторона молчит большую часть времени, пропуск таких чанков до `transcribe`
срезал бы стерео-ASR заметно без потери качества; проверять DER-стендом.

Моно: 789 с на часовке (RTF 0,22) — вторая статья после ASR. Горячие точки
по коду (профилировка оценочная, по чтению, не замер):
1. `_extract_segment_features` (MFCC-13 + centroid/rolloff + покадровый pitch
через автокорреляцию) считается для КАЖДОГО turn безусловно
(`mono_diarizer.py:427–428`), даже когда CAM++-путь успешен и акустика не
нужна, — ленивое вычисление только для fallback-ветки убрало бы главный
кусок librosa-нагрузки без изменения поведения CAM++-пути.
2. Per-turn melspectrogram 80 полос для CAM++ — необходим, но считается
с паддингом коротких реплик до 0,8 с (перекрытие соседней речью).
3. `silhouette_score` O(n²) на ~1000 эмбеддингах для защиты от ложного
сплита монолога — дёшево относительно п.1, но тоже в wall.
Ускорять ценой DER запрещено без перемера `der_suite` (ориентир DER держать
0,163/роли 0,94): любая чинка моно-диаризации — только с зелёным DER-стендом.

Вывод: на стерео с раздельными каналами диаризация не нужна (код уже так
и делает); ускорение моно — ленивые acoustic-фичи + energy-gating стерео,
оба — отдельными пунктами с DER-контролем, в этом заходе код не менялся.

### §21. T-one как движок длинного пути на small (п.4, оценка без включения)

Все цифры WER/скорости — из уже лежащих в репозитории запусков скриптов
(`scripts/eval_wer.py`; ограничения выхода — чтением `app/asr/tone_engine.py`):

| набор | podlodka (длинный) WER clean/tel | T-one WER clean/tel | источник |
|---|---|---|---|
| Golos-100 | 18,4 % / 35,2 % | 16,1 % / 19,6 % | `reports/wer_golos100.json` |
| RuLS-296 | 9,8 % / 10,5 % | 6,0 % / 7,9 % | `reports/wer_ruls296.json` |
| SOVA-265 | 13,7 % / 15,9 % | 13,0 % / 11,6 % | `reports/wer_sova265.json` |

Скорость (§18, те же скрипты): проход 296×2 — podlodka ~1600 с против T-one
~110 с; 265×2 — ~1060 с против ~75 с, т.е. голосовой путь быстрее длинного
в ~11–14 раз. Проекция на часовку: ASR-этап 3687 с / ~12 ≈ ~300 с — самый
сильный из всех рассмотренных рычагов по wall.

Почему всё равно не включается (проверено кодом, не мнением):
- Выход T-one — строчные без пунктуации по построению: алфавит CTC
`LABELS = "абвгдеёжзийклмнопрстуфхцчшщъыьэюя "` (`tone_engine.py:25`),
декодер возвращает склейку букв без регистра и знаков; нормалайзер
пунктуацию не восстанавливает (он нормализует, а не расставляет).
- Слововых таймкодов нет: `"words": []` всегда (`tone_engine.py:419`) —
  требование C2 «таймкоды сегментов и слов» невыполнимо.
- Уверенность — прокси (средний max-posterior по непустым кадрам), язык
  всегда `"ru"` без детекции, вход только 8/16 кГц PCM.
Требования C2 (пунктуация, регистр, таймкоды слов, уверенность) закрывают
3 из 4 мимо; C8 (SRT/VTT/поиск по пунктуированному тексту) и ITN-цепочка
тоже рассчитаны на whisper-выход. T-one остаётся движком голосового пути
(дефолт по ADR-015 — короткие запросы, где контракт ограничивается текстом).

Решение по задаче: в длинный путь по умолчанию НЕ включать — код не менялся,
флаг не добавлялся. Включение — только отдельной записью в `docs/decisions.md`
(ADR) с одновременным изменением контракта C2/C8, отдельным пунктом и
перемером WER/DER/SRT на часовке. Данный §21 — требуемая оценка, не ADR.

Выводы (каждый — строкой таблицы, не мнением):
- **beam_size=1 — бесплатно везде**: ΔWER 0…−0,3пп на 5 из 6 клеток, +0,4пп на
  одной (SOVA clean — шум выборки 25 файлов); RTF на коротких не меняется
  (доминирует overhead), на длинной из §12 — 0,292 против 0,305. Потерь нет
  нигде — единственный рычаг без цены. Лучший вариант для повторной часовки
  (п.5): beam=1.
- **int8 — уже оптимум**: `ASR_COMPUTE_TYPE=int8` запинён в compose для
  worker-long и `.env`; альтернативы CTranslate2 (float32/float16) на CPU
  только тяжелее и медленнее при том же качестве — варьировать нечего,
  измерять нечего.
- **Быстрый VAD — не рычаг**: скорости не даёт (RTF в шуме ±0,5 %), а на
  телефонии местами вредит (Golos tel +1,9пп, RuLS tel +0,3пп; SOVA tel
  −0,4пп — в другую сторону, т.е. шум/домен). Дефолт VAD (450/300) оставить.
- **Без VAD (G) — только референс**: на коротких Golos лучше всех
  (0,0909/0,2013), на RuLS/SOVA нейтрально — но длинному пути VAD нужен для
  сегментации чанков (см. §12 вывод G), в прод не предлагать.
- **word_timestamps=False — −0…7 % RTF ценой контракта**: текст (и WER)
  идентичен везде, выигрыш заметен только на коротких с большим overhead
  (Golos −6…7 %, SOVA −2…3 %, RuLS ~−1 %). Цена — потеря слововых таймкодов,
  требуемых C2 (сегменты/слова/SRT). Не включать.
- **Меньшие чанки — точнее, но дороже**: x3 лучше x1 по WER везде
  (Golos −5,2/−2,0пп, RuLS −1,1/−2,5пп, SOVA 0/−0,8пп), но RTF выше
  (+6 % / +12 % / +38–41 % — на SOVA с её паузами overhead трёх вызовов
  особенно заметен). Продовые чанки 600 с резать ради WER нельзя без
  перемерки часовки: выигрыш в пп против проигрыша в RTF при цели ≤ 1,0.
- Оговорка: склейка-x1 хуже пофайлового корпусного WER (Golos 0,156 против
  0,110; RuLS 0,111 против 0,092; SOVA 0,174 против 0,095) — на длинных
  файлах декодер дрейфует сильнее; пофайловые цифры оптимистичны к часовке.

Итого для п.5: повторная часовка — прод + beam_size=1, остальное без изменений.
