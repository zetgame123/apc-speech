# Известные ограничения и компромиссы (Known Issues & Technical Debt)

Документ фиксирует архитектурные допущения, границы применимости и осознанные компромиссы сервиса `apc-speech`.

---

## 1. Ограничения профиля `small` (2 vCPU / 4 GB RAM)
* **Семантический анализ звонков**:
  * На профиле `small` невозможно запустить локальную LLM масштаба 7B–14B (модель требует $\ge 5$ ГБ RAM в квантовании Q4_K_M и перегрузит CPU).
  * На этом профиле семантический разбор выполняется **детерминированным rule-based адаптером** на базе YAML-таксономии и регулярных выражений. Он извлекает сущности, таксономию и чек-лист со 100% соблюдением JSON-схемы, но не обладает способностью делать свободные выводы по нестандартным формулировкам.
  * Для глубокого нейросетевого разбора через `llama.cpp` требуется запуск профиля `local-full` (`docker compose --profile local-full up`).

## 2. Диаризация в моно-записях
* В стерео-записях с раздельными каналами участников разделение спикеров является аппаратным и дает абсолютную надежность ($DER \approx 0\%$).
* В моно-записях разделение спикеров основано на нейросетевых d-векторах и эвристиках приветствия. Если оба участника одного пола с очень близким тембром голоса и перебивают друг друга каждые 2 секунды, точность классификации ролей может снижаться. В таких пограничных случаях система намеренно **не додумывает роли**, а выставляет нейтральные метки `participant_1` / `participant_2` с флагом `role_confidence=low`.

## 3. Языковой охват
* Сервис полностью сфокусирован на **русской речи**:
  * Словарь отраслевых подсказок (hotwords) и обратная нормализация текста (ITN) заточены под русские числительные, даты, размеры щитов («3х6») и города РФ.
  * Движок `faster-whisper` мультиязычен и способен распознавать английскую речь при явном указании параметра `language=en`, однако расширенная нормализация английского текста является задачей будущих релизов.

## 4. Конкурентная нагрузка на диск при загрузке тяжелых файлов
* При одновременной загрузке десятков файлов по 500 МБ сеть и диск MinIO могут испытывать пиковую нагрузку.
* Рекомендуется в продакшн-контуре использовать загрузку по S3 presigned URLs или через эндпоинт `POST /v1/jobs/by-url` с прямым указанием пути во внутреннем хранилище.

## 5. Latency голосового поиска на CPU без AVX2 (требует повторного замера)
* Измеренный на разработческой машине (CPU без набора инструкций AVX2) замер `voice/search` для `test.mp3`
  составил 82,7 с (холодный запуск) / 149,7 с (повтор) — норматив $\le 2{,}5$ с не выполнен (см.
  `docs/benchmark-report.md`, раздел 2 и 3.1).
* ASR голосового поиска уже изолирован от `api` в отдельный процесс `worker-fast` через выделенную
  Redis-очередь (`jobs:audio:fast`) — это устраняет конкуренцию за CPU между запросами, но не компенсирует
  отсутствие AVX2/AVX512 у конкретного CPU, которое является определяющим фактором скорости инференса
  `faster-whisper`/CTranslate2.
* Аномальное замедление повторного запроса (149,7 с > 82,7 с холодного) не объяснено тепловым троттлингом
  CPU и требует отдельного профилирования — возможный кандидат: деградация производительности треда ASR при
  повторном обращении на связанном CPU-квотой контейнере.
* Требуется повторный замер на целевом железе заказчика (с поддержкой AVX2) перед финальной приёмкой по
  критерию производительности (`brief.md`, раздел «Качество и скорость»).

## 6. Замер B1 на Docker Desktop (Windows-хост, Linux VM без AVX2, 2026-10-11)

* Стенд: `docker compose -p apc_clean up -d --build` (профиль `small`), 12 CPU / 8 ГБ у демона.
  Все 8 сервисов поднялись healthy; `/health` (small), `/ready` (все true), `/metrics` — 200.
  Egress-изоляция подтверждена живьём: `worker-long`/`worker-fast` — curl exit 6 (наружу не ходят),
  `api`/`worker-callback` — HTTP 200.
* Сквозной звонок (11,2 с, телефония 8 кГц): задание `queued → running → succeeded` за ~4 мин
  (холодная загрузка podlodka-turbo-ct2 ~31 с на квоте 0,6 CPU + ASR ~2,5 мин + диаризация).
  Транскрипт (4 сегмента, роли), разбор по схеме (`schema_version 1.0.0`, `prompt_version v1.2`,
  `inquiry_type=pricing`), кластеризация `POST /v1/texts/analyze` — корректны. Поллинга e2e-скрипта
  (20×2 с) на холодный старт не хватает — задание досматривалось вручную.
* Голосовой поиск НЕ укладывается в SLA на этом железе: прогрев есть, но запрос 3 с →
  стабильно 503 `voice_search_timeout` (~3,1 с при лимите ожидания 2,4 с), и для 8 кГц,
  и для 16 кГц входа. Прямой замер инференса внутри контейнера: 3 с аудио → **43 с** при
  `cpu_threads=1`, **~23 с** прямым вызовом без промпта, **7,0 с** при `cpu_threads=4`.
  Причина: в VM доступен только флаг `avx` (нет AVX2/FMA/VNNI) — int8-ядра CTranslate2
  деградируют на порядок; это тот же класс железа, что уже зафиксирован в п.5.
* Вывод: на железе без AVX2 SLA 2,5 с недостижим никакими настройками потоков/квот (проверено: квота 0,5→2 CPU не меняет картину; 1 поток только
  хуже). Потоки CTranslate2 оставлены по умолчанию (2), поджаты только BLAS-переменные.
  Требуется повторный замер voice-search на целевом железе с AVX2 до приёмки C4.

## 7. Замер C4 на целевом железе с AVX2 (Ryzen 7 8845HS, 2026-10-11)

* Стенд: Arch Linux, Ryzen 7 8845HS (AVX2+AVX512 есть), `apc_small` с `docker-compose.bench-small.yml`
  (cpuset 4,6 — разные физические ядра), governor `powersave`, pinned-ядра наблюдались на 0,4–1,4 ГГц
  при max 3,8 ГГц. APP_PROFILE=local-full из `.env`, llm-runtime не поднимался.
* HTTP-замер (`scripts/benchmark_load.py --matrix`, 3/10 с × 8/16 кГц, прогрев + 20 повторов
  последовательно): **84/84 → 503, доля 503 = 1,0**. В штатном окне 2,4 с — `voice_search_timeout`
  за ~3,1 с. Полный отчёт: `reports/voice_c4_small_2026-10-11_ryzen8845hs.json`.
* Движковый замер (прогретый `transcribe()` внутри `worker-fast`, 5 прогонов): медиана
  **s3_16k 17,6 с; s3_8k 18,4 с; s10_16k 17,9 с; s10_8k 36,4 с**; загрузка модели 16 с, прогрев 35 с.
  SLA 2,5 с превышен в **7–14 раз**. Движок и пороги ради замера не менялись.
* Вероятные причины (измерено, не предположения): pinned-ядра на низкой частоте (powersave без
  boost под нагрузкой пина), все 8 сервисов делят те же 2 ядра, whisper-small с beam=2 + промпт +
  hotwords + VAD. Длительность почти не влияет (3 с ≈ 10 с ≈ 18 с) — доминирует вес модели, а не аудио.
* Попутная находка (баг, не причина провала): `wait_fast_result` через `BLPOP` упирается в чтение
  сокета redis-py 8.1.0 ~5 с без явного `socket_timeout` (`TimeoutError: Timeout reading from redis`,
  проверено изнутри `api`: с `socket_timeout=35` блокировка держит 30 с). Любое окно ожидания >5 с
  сейчас неработоспособно — отдельный пункт для починки (не порог SLA, а клиент очереди).

  s3_8k 7,12 с; s10_16k 6,89 с; s10_8k 14,59 с**; прогрев 10,7 с. SLA превышен в **2,7–5,8 раз**.
* Загрязнённый прогон (параллельно дренировалась очередь, ~2,7x инфляция: 19,1/19,6/18,9/39,9 с)

  код в `app/workers/fast_voice_search.py`, тесты `tests/test_voice_fast_variants.py`).

## 10. Почему 10 с/8 кГц вдвое медленнее 10 с/16 кГц (2026-10-11)

* Метод: прямые вызовы `AsrEngine.transcribe()` в контейнере `worker-fast` (тот же образ/модель/потоки/cpuset),
  по стадиям: препроцессор отдельно, транскрипция отдельно, плюс число сегментов/тексты.
* Исключено замерами: препроцессор (ffmpeg loudnorm+ресемплинг 8→16 кГц) стоит всего **215–404 мс**;
  температурный fallback отсутствует по построению — `temperature=0.0` скаляр, а faster-whisper 1.2.1
  заворачивает в цикл только список (`temperature if isinstance(temperature, (list, tuple)) else [temperature]`,
  проверено чтением установленного исходника) — флага не потребовалось, код не менялся.
* Причина: **галлюцинированный повтор на апапсемпленном 8 кГц аудио**. 10 с/16 кГц → 1 сегмент
  (52 символа, 7,4–7,6 с); те же 10 с из 8 кГц → **3 сегмента, 125 символов, 14,7–14,8 с**:
  модель дважды дописывает «Здравствуйте, агентство, наружной рекламы слушаю вас.».
  Каждый лишний сегмент — полный прогон beam=2, отсюда ×2.
* Триггер: достаточно **либо** `initial_prompt` (510 симв.), **либо** `hotwords` (384 симв.)
  по отдельности (9,3 с / 8,9 с, 3 сегмента); без обоих — 1 сегмент за 5,6 с.
  На коротких 3 с петля не срабатывает (7,1 против 6,8 с — разрыв в пределах шума).
* VAD-чанки одинаковы (те же байты после препроцессора, те же параметры) — расхождение именно
  на декодировании, не на детекции речи. Пустотные частоты >4 кГц после апсемплинга +
  длинная подсказка уводят декодер в повтор.
